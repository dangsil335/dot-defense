# 고유장비 시스템 설계 (캐릭터 고유유물 → 고유장비 전환)

작성일: 2026-07-21
현재 버전: v674

## 목표

캐릭터마다 **고유 장비**를 부여하고, 돌파(★)에 따라 옵션이 해금되며, 다른 캐릭터가 장착하면
그 캐릭터의 능력을 이식받게 한다. 목적은 **캐릭풀을 여러 개 해금할 동기 부여**.

기존 "캐릭터 → 고유 고대유물"(SSR 7명 전용, 인런 픽업)을 대체한다.

---

## 1. 확정된 구조

### 1.1 슬롯 — 5번째 독립 슬롯

현재 장비 슬롯은 4개 고정: `GEAR_SLOTS = ['offense','targeting','supply','control']` ([index.html:6528](../../../index.html)).
여기에 **5번째 슬롯 `signature`(고유)** 를 추가한다.

**고유장비는 세트 4피스 카운트에 넣지 않는다.** 현재 4피스 = "4슬롯 전부 같은 세트"인데,
고유장비가 기존 슬롯 하나를 차지하면 세트가 깨진다. 별도 슬롯 + 세트 카운트 제외로
**기존 4슬롯 세트를 온전히 유지하면서 고유장비를 낀다.**

단 고유장비는 세트 보너스의 **수혜자**다 — 다른 4슬롯이 세트를 이루면 그 metaMods 버프는
고유장비의 능력 강화 옵션에도 자연히 적용된다(같은 출력 버스 `applyGearEffects` → `state.metaMods`).

### 1.2 캐릭터 연결 — charId 1:1

현재 장비↔캐릭터 연결은 **세트 단위 소프트 매칭**이다([index.html:6680](../../../index.html)):
세트가 캐릭터 *리스트*를 갖고(`GEAR_SETS[set].affinity`), 매칭 시 옵션값 풀·미매칭 시 ½.

고유장비는 이를 **1:1로 조인다**: 아이템에 `charId` 필드를 박고 `curChar === item.charId`로 판정.
이것이 "세트 캐릭터" 판정의 기준이다.

### 1.3 옵션 — 3라인 고정 + 돌파별 해금

고유장비는 최상 등급이므로 **3라인 고정**. 각 라인은 평소 일반 옵션 풀에서 롤(기존 T1~T5 등급 그대로,
[index.html:6585](../../../index.html)). 돌파에 따라 **라인별로 고유 옵션이 롤 풀에 진입**한다:

| 라인 | 해금 | 등장하는 고유 옵션 | 작동 조건 |
|---|---|---|---|
| **옵션3** | 0돌파부터 | 시그니처 능력 일반 강화 (**낮은 확률**) | **본인 전용** |
| **옵션2** | **4돌파** | **서브능력(별돌파 4★) 고유 메커니즘 옵션** | **본인 전용** |
| **옵션1** | **8돌파** | **메인능력(시그니처 t1) 고유 메커니즘 옵션** | **본인 전용** |

해금 전엔 그 라인도 일반 옵션만 롤된다. 기존 리롤/잠금이 **라인 인덱스로 작동**하므로
(`_gearLocks.has(i)`, [index.html:36035](../../../index.html)) 리롤로 원하는 고유 옵션을 노릴 수 있다.

> **주의(현행과 다름):** 현재 일반 장비의 라인 수는 등급별 1/2/2/3이고 인덱스 0은 아키타입 시그니처로 예약돼 있다.
> 고유장비는 **자체 3라인 고정 레이아웃**을 별도로 정의한다(기존 규칙을 토글하는 게 아님).

#### 고유 메커니즘 옵션이란 — 수치가 아니라 규칙을 바꾼다

단순 배율 증가("데미지 +30% → +60%")는 밋밋하고 캐릭터 개성이 드러나지 않는다.
대신 **그 캐릭터 핵심 메커니즘의 상수 자체를 바꾼다**:

| 캐릭터 | 핵심 메커니즘 상수 | 고유 옵션 예 |
|---|---|---|
| 페리아 | 극성 최대 20체 / 충돌 쿨 20프레임 | 극성 상한 **32체** / 같은 극 충돌 피해 **2배** |
| 트리나 | 환영 1기 / 피해 합산 캡 +90% | 환영 **+1기** / 캡 **150%** |
| 아이리스 | 프레임 내 적 N체 도달 시 섬광 | 발화 임계 **-2체** / 잔상 지속 **2배** |
| 카이라 | 3초마다 야수⇄인간 전환 | 야수형 지속 **2배** |
| 갈라테아 | 석화 완전정지 | 석화 지속 **+50%** |

숫자가 아니라 **그 캐릭을 쓰는 방식이 바뀐다**(트리나 환영이 4기가 되면 빌드가 달라진다).

#### ⚠️ 본인 전용 하드 게이트 (핵심 제약)

**고유 메커니즘 옵션은 세트 캐릭터 본인이 장착했을 때만 작동한다. 타 캐릭 장착 시 완전 비활성.**

이유: 타 캐릭은 이 장비로 **능력을 이식받는데**(§1.6), 고유 강화까지 받으면
"타 캐릭이 본인보다 그 능력을 더 잘 쓰는" 본말전도가 된다.
타인은 **능력을 빌려 쓰되 기본 성능으로만** 쓴다.

기존 affinity는 매칭 1.0 / 미매칭 0.5의 **소프트** 차등이지만([index.html:6680](../../../index.html)),
고유 메커니즘 옵션은 **하드 게이트**(작동/비작동)다.

**UI 표기 필수:** 옵션 라인에 `🔒 카이라 전용` 배지를 달고, 타 캐릭 장착 시 회색 비활성으로 표시한다.
(기존에 affinity 배지를 `동조` / `동조 ½`로 구분 표기하는 선례가 있다 — [index.html:6607](../../../index.html))

### 1.4 SSR 전용 — 고정 고유 패시브

**SSR 7명의 고유장비만** 3라인 옵션에 더해 **고정 고유 패시브**를 갖는다.
옵션은 굴려야 나오는 확률적 가치인 반면, 이 패시브는 **굴림 없이 확정적으로 붙는** 가치라
SSR 위상이 분명해진다(기존 "유물 = SSR 표식"의 대체).

기존 고대유물 효과가 정확히 이 형태이므로 **그대로 계승**한다
([index.html:18830](../../../index.html), kairaFang 예):

```js
const baseDmg = synergy ? (1.34 + stars*0.08) : (1.15 + stars*0.05);
st.metaMods.dmgMul *= baseDmg;
st.metaMods.luckyChanceBonus += synergy ? 0.08 : 0.04;
```

- **star 스케일**: 돌파할수록 강해짐
- **synergy**: 본인(세트 캐릭터) 장착 시 큰 폭 증폭, 타 캐릭 장착 시 축소
- 밸런스가 이미 검증된 값이므로 마이그레이션이 안전

| | SR 13명 | SSR 7명 |
|---|---|---|
| 3라인 옵션 (돌파 해금) | ✅ | ✅ |
| 고정 고유 패시브 | ❌ | ✅ |

### 1.5 돌파 — 캐릭터 ★와 연동

고유장비의 star는 **캐릭터 star에 연동**한다. 가챠에서 캐릭터를 중복으로 뽑아 돌파하면
그 고유장비도 같은 star가 된다. `META.charStars` 재사용, 별도 돌파 재화 없음.

> **현행과 다름:** 기존 유물의 ★4/★8 각성은 **2게이트**였다 —
> 영구 star ≥4/8 **+ 인런에서 그 캐릭 trigger 능력 max**(`checkAncientAwakening`,
> [index.html:18841](../../../index.html)). 고유장비의 옵션 해금은 **순수 star 임계**로 단순화한다
> (장비 스탯은 런 시작 시 무조건 적용되는 기존 장비 규칙과 일치).

### 1.6 장착자 분기 — 본인은 강화, 타인은 이식

**메인 = 시그니처 t1** (예: 카이라 `huntingClaw`) / **서브 = 별돌파 4★** (예: `beastForm`).

| | 본인 장착 | 타 캐릭 장착 |
|---|---|---|
| 일반 옵션 (평범~높은 등급) | ✅ | ✅ |
| **고유 메커니즘 옵션** | ✅ | ❌ **완전 비활성**(§1.3) |
| 능력 이식 (4★ 서브 / 8★ 메인) | 불필요(이미 보유) | ✅ |
| SSR 고유 패시브 | synergy 배율 (강) | 기본 배율 (약) |

- **세트캐릭 본인 장착** → 고유 메커니즘 옵션 전부 활성 + SSR 패시브 synergy. **자기 킷 극대화**.
- **다른 캐릭 장착** → 세트캐릭 능력을 **보유하고 런 시작**:
  - **4돌파** → 서브능력(별돌파 4★) 갖고 시작
  - **8돌파** → 메인능력(시그니처 t1) 갖고 시작
  - 단 이식받은 능력은 **기본 성능**으로만 작동(고유 메커니즘 옵션 비활성)

**설계 의도:** 타인은 "능력을 빌려 쓰는" 폭넓은 조합 실험, 본인은 "그 캐릭터의 진가".
서로 다른 가치라 둘 다 쓸 이유가 생긴다.

**슬롯 예산:** 현재 모든 런은 `shot` 하나로 시작한다([index.html:20199](../../../index.html) —
진화트리 개편으로 `startAbilities`는 사실상 폐기됨). 이식 능력은 **시작 액티브 슬롯을 하나 추가**로 차지한다.
고유장비 슬롯이 1개이므로 "어느 캐릭 능력을 갖고 시작할지"를 장비 선택으로 정하는 셈 —
이것이 **여러 캐릭 돌파 → 여러 조합 실험**이라는 수집 동기의 핵심이다.

## 2. 데이터 스키마

```js
// 고유장비 아이템 (기존 gear 아이템에 charId·stars 추가, slot 고정)
{
  id: 42,
  slot: 'signature',        // 신규 5번째 슬롯
  charId: 'kaira',          // 1:1 캐릭터 연결 (세트캐릭 판정 기준)
  rarity: 'unique',         // 최상 등급 (신규 — GEAR_RARITY / GEAR_RARITY_LINES 에 unique:3 추가)
  level: 0,                 // 기존 장비 레벨 (0~20, gearGold)
  lines: [ /* 3개 고정 */ ],
  locked: false,
  // ⚠️ set 필드 없음 — 고유장비는 어떤 세트에도 속하지 않는다(_gearSetCounts 에서 제외).
  //    기존 4슬롯 세트를 깨지 않기 위한 설계(§1.1).
  // ⚠️ stars 필드 없음 — META.charStars[charId] 에서 읽는다(§1.5 연동).
}

// 캐릭터 테이블(데이터 리팩터 시)에서의 표현
kaira: {
  // ...
  uniqueGear: {
    // SSR 만: 고정 고유 패시브 (기존 유물 효과 계승)
    passive: {
      base:    { dmgMul: 1.15, starStep: 0.05, luckyBonus: 0.04 },
      synergy: { dmgMul: 1.34, starStep: 0.08, luckyBonus: 0.08 },
    },
  },
  // 이식 대상은 별도 필드 불필요 — 메인=CHAR_SIG_ABILITIES[id][0], 서브=CHAR_STAR_UNLOCKS[id][4] 에서 도출
}
```

**도출로 처리(테이블에 넣지 않음):** 이식할 메인/서브 능력 id는
`CHAR_SIG_ABILITIES[charId][0]`(메인)과 `CHAR_STAR_UNLOCKS[charId][4]`(서브)에서 계산한다.

## 3. 기존 시스템과의 관계

| 기존 | 처리 |
|---|---|
| 고대유물 7종 (`RELICS` 중 `isAncient`) | 해당 SSR의 **고유장비 패시브로 전환**. 유물 정의는 폐기 |
| `META.ancientRelics[rid].stars` | 폐기 — star는 `META.charStars` 로 일원화. **기존 보유자 마이그레이션 필요** |
| 인런 유물 픽업 (`activeRelics`, `_charRelicEv`, `CHAR_AMBUSH` 유물 이벤트) | 폐기 — 장비는 상시 장착이므로 인런 획득 개념이 사라짐 |
| 가챠 `ancientRelicPool` / `ancientRelicRate` (0.5%) | 폐기 — 고유장비는 캐릭터 해금 시 자동 지급 |
| `checkAncientAwakening` / `activateAncientAwaken` (2게이트 각성) | 폐기 — 순수 star 임계로 단순화 |
| 세트 affinity 소프트매칭 | **유지** (일반 장비용). 고유장비만 charId 1:1 판정 |
| 리롤/잠금 (`_gearLocks`) | **유지·재사용** — 고유장비 옵션 리롤에 그대로 적용 |
| `applyGearEffects` → `metaMods` | **유지** — 고유장비도 같은 버스 사용 |
| 능력 부여 `_shopGainAbility` ([31094](../../../index.html)) | **재사용** — 런 시작 이식에 사용 |

## 4. 선행 작업 — 별돌파 12종 신규

"서브 = 별돌파 4★"이므로 **별돌파가 없는 SR 6명**은 서브 자리가 빈다:
**에이미 · 클로에 · 라라 · 갈라테아 · 트리나 · 아이리스**.

이 6명에게 4★/8★ 별돌파 능력 **12종을 신규 설계**해 20명 전원이 동일 구조를 갖게 한다.
(카르디스타·레비나에 4종을 추가한 v674 작업과 동일한 경로: 능력 정의 → `CHAR_STAR_UNLOCKS` →
`ABILITY_ICON_ORDER` → `ABILITY_TAGS` → `TD_UNLIMITED_RANGE_IDS`. 비용은 `isStarUnlock`이라 자동 3.0)

## 5. 단계 제안

규모가 크므로 독립 배포 가능한 단위로 나눈다.

| 단계 | 내용 | 비고 |
|---|---|---|
| **0-a** | 별돌파 12종 (6명 × 2) | 선행 필수 — 서브능력 공백 해소 |
| **0-b** | **능력 수치 `stats` 데이터화** | 고유 메커니즘 옵션의 **선행 조건**(§7) — 최소한 옵션이 건드릴 상수만이라도 |
| **1** | 5번째 슬롯 + 고유장비 아이템 생성/장착/UI | 세트 카운트 제외 확인 |
| **2** | 3라인 옵션 + 돌파별 해금 + 리롤 연동 | 고유 옵션 풀 신규 · **본인 전용 하드 게이트 + UI 배지** |
| **3** | **캐릭터별 고유 메커니즘 옵션 설계·구현** | 최대 작업(§6). 단계 2의 틀 위에 캐릭터별로 채움 |
| **4** | SSR 고유 패시브 (유물 7종 효과 이전) | 유물 → 장비 마이그레이션 |
| **5** | 능력 이식 (런 시작 부여) | 슬롯 예산 처리 |
| **6** | 구 유물 시스템 정리 + 보유자 데이터 마이그레이션 | 되돌리기 어려우므로 마지막 |

## 6. 미결 — 구현 중 결정하거나 플레이테스트로

- **캐릭터별 고유 메커니즘 옵션 20명분 설계** ← A 방향 채택으로 새로 생긴 최대 작업.
  각 캐릭터의 핵심 상수를 파악하고 "무엇을 바꿀 것인가"를 정해야 한다(§1.3 표는 5명 예시일 뿐).
  캐릭터당 최소 2종(메인용·서브용)이면 **40종**. 밸런스가 제각각이라 일괄 공식으로 못 뽑는다.
- **옵션3 고유 옵션 등장 확률**: "낮은 확률"의 구체값.
- **이식 능력의 슬롯**: 시작 슬롯을 +1 늘릴지, 기존 예산 안에서 소비할지.
- **기존 유물 보유자 보상**: `META.ancientRelics`에 star가 쌓인 유저를 어떻게 전환할지
  (제안: 해당 캐릭 star로 이관하거나 별조각 환급).
- **SR 고유장비의 가치**: SSR은 고정 패시브로 차별화되지만, SR 고유장비가 일반 레전드 장비보다
  나은 이유가 "능력 이식 + 캐릭 전용 강화 옵션"뿐인지 검토 필요.

## 7. 데이터 테이블 리팩터와의 관계

이 설계는 진행 중이던 **캐릭터/능력 데이터 테이블화**([2026-07-21-data-table-example.md](2026-07-21-data-table-example.md))에
직접 영향을 준다:

- 캐릭터 레코드의 `relic` 필드가 **`uniqueGear`로 대체**된다.
- SSR만 `uniqueGear.passive`를 가지므로, 등급별 필드 유무 패턴이 유지된다.
- 이식 능력(메인/서브)은 **도출**이므로 테이블에 넣지 않는다.

따라서 **이 시스템을 먼저 확정한 뒤 데이터 테이블 스키마를 확정하는 것이 맞다.**

### ⚠️ 단, 능력 `stats` 데이터화는 이 기능의 선행 조건에 가깝다

고유 메커니즘 옵션(§1.3)은 "그 캐릭터 핵심 상수를 바꾸는" 것인데, 그 상수들이 지금은
능력 `tick` 본문에 하드코딩돼 있다. 예: 페리아의 극성 상한 20은 `polarField.tick` 안의 리터럴이다.

- **지금 구조로 하면:** 옵션 하나마다 해당 능력에 특수 분기를 심어야 한다 → 캐릭터 20명 × 옵션 2종 = 40곳의
  ad-hoc 코드. 이번 세션에 반복해서 겪은 "하드코딩 산재 → 누락 버그"를 그대로 재생산한다.
- **`stats` 데이터화 후:** "옵션이 `stats.polarCap`을 20 → 32로 덮어쓴다"로 끝난다. 일괄 처리 가능.

그래서 단계 **0-b**를 넣었다. 전면 리팩터까지 갈 필요는 없고, **고유 옵션이 건드릴 상수만
`stats`로 노출**해도 충분하다.
